# 要件定義

## 1. 対象

モバイルブラウザを主利用環境とする Web アプリ。PWA 対応を前提に検討する。

## 2. 機能要件

### FR-01 認証
- ソーシャルログインを中心とした方法でサインインできる。
- MVP の Provider は Google を第一候補とする。
- Apple Login は必要性と運用コストを確認して追加判断する。
- 長期間利用しないケースを想定し、アカウント復旧性を重視する。

### FR-02 手紙を書く
- 本文を自由入力できる。
- カテゴリ・タグの入力を要求しない。
- 写真を任意で添付できる。
- 位置情報を任意で添付できる。
- 下書きは自動保存する。

### FR-03 届ける時期
- 数日後くらい
- 数週間後くらい
- 数か月後くらい
- 1年後くらい
- 未来に任せる

実際の到着予定日時は、選択した期間内でシステムが決定する。

### FR-04 封
- **封をする**: 到着までユーザー UI から本文・添付を閲覧不可
- **封をしない**: 送信後も本文・添付を閲覧可能
- いずれも送信後は内容を編集できない。

### FR-05 送信確認
送信直前に届ける時期・封・添付の有無を確認する。CTA は「未来へ送る」。

### FR-06 送信後
- 送信済みの手紙は「未来を旅する手紙」として確認できる。
- 本文編集・添付変更・配送設定変更は不可。
- 手紙は削除できる。
- 送信直後の誤操作救済として短時間の Undo を検討する。

### FR-07 到着
- 到着予定を満たした手紙はサーバー側で `delivered` に遷移する。
- 到着時に通知を送信する。
- 通知本文には手紙本文・写真を表示しない。

### FR-08 受信箱
- 届いた手紙を一覧表示する。
- UI 表現は「未読 / 既読」より「未開封 / 開封済み」を優先する。
- 未開封のまま後日読むことができる。
- 「何日前の自分から」など、経過時間を主要情報として表示する。

### FR-09 開封
封をした手紙は本文表示前に開封画面を表示する。

### FR-10 返信
- 開封済みの手紙に返信できる。
- 返信も未来へ送る。
- 返信時にも届ける時期と封の有無を選べる。
- MVP は一通につき次の一通へ続く一本道のスレッドとする。

### FR-11 削除
- ユーザーは自分の手紙を削除できる。
- 旅の途中で削除した手紙は未来へ到着しない。
- 削除は編集不可ルールとは別の安全・プライバシー上の救済として扱う。

## 3. 非機能要件

### NFR-01 プライバシー
- ユーザー A はユーザー B の手紙を取得できない。
- Backend では Convex function によるサーバー側アクセス制御を必須とする。
- 通知にプライベート内容を表示しない。

### NFR-02 信頼性
- 配送ジョブは冪等であること。
- 同じ手紙が二重到着しないこと。
- 通知送信失敗が手紙の到着状態を破壊しないこと。

### NFR-03 モバイル UX
- 主要操作を片手操作できるサイズ・配置にする。
- 長文作成中のデータ消失を防ぐ。
- 低速回線・一時的オフラインを考慮する。

### NFR-04 アクセシビリティ
- タップ領域、コントラスト、フォーカス、スクリーンリーダーを考慮する。
- 状態を色だけで表現しない。

### NFR-05 時刻
- DB の時刻は UTC で保持する。
- UI はユーザーのタイムゾーンで表示する。

## 4. 未決事項

- 正確な配送レンジをどこまで固定仕様にするか
- 「未来に任せる」の最短 / 最長期間
- 削除を論理削除にするか物理削除にするか
- Web Push が使えないユーザー向けにメール通知を MVP に含めるか
- 写真の最大枚数・サイズ
- 位置情報の粒度
